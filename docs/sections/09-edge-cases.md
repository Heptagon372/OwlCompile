## 9. 엣지 케이스와 장애 대응

폰·진행자 PC·보드가 끊기거나 새로고침되거나 서로 경쟁하는 상황을 "상황 → 감지 → 시스템 동작 → 진행자 행동"으로 정리한다. 원칙: (1) DB 행이 유일한 진실이고 모든 화면은 `loadGameSnapshot` 재조회로 복구한다(섹션 03). (2) 전이·실행·결과 쓰기는 진행자 탭 하나만 하며 전부 조건부(CAS)이거나 멱등이다. (3) 폰의 저장 안 된 로컬 상태는 지키지 않는다 — 충돌하면 서버가 이긴다. (4) 판정이 애매하면 비상 버튼(§9.7)으로 되돌린다.

### 9.1 공통 장치

- **[결정]** 진행권: `games.host_tab text` 컬럼을 추가한다(섹션 03 스키마 보강). `/host`는 로드마다 메모리에 `crypto.randomUUID()`를 만들어 즉시 `host_tab`에 쓴다 — 마지막으로 연 탭이 진행권을 가진다. `host_tab ≠ 내 id`를 받은 탭은 버튼을 전부 끄고 오버레이 "다른 창에서 진행 중이에요 [여기서 진행]"을 띄우며 만료 감지·autoplay 타이머를 멈춘다.
- **[결정]** `games` 쓰기는 기대 페이즈와 진행권을 조건으로 건다. 0행이면 다른 탭이 먼저 했거나 진행권을 잃은 것이므로 스냅샷만 다시 읽는다. 네트워크 실패는 1·2·4초 3회 재시도 후 빨간 토스트.

```ts
// lib/host/phases.ts — games 쓰기의 유일한 모양
const { data } = await supabase.from('games').update(patch)
  .eq('id', gameId).eq('phase', expected).eq('host_tab', myTab).select('id');
if (!data?.length) return reloadSnapshot();   // 이중 전이 없음
```

- **[결정]** 상태 기반 진행: 진행자 화면은 버튼 이벤트가 아니라 스냅샷에서 할 일을 도출한다. `sealed`인데 `submitted_at is null`인 팀 → 자동 제출. `running`에서 `results`가 없는 팀 → `submit_order` 순으로 실행하고, 결과가 있는 팀은 다시 돌리지 않는다. 다음 팀 전환 시각 = `running_started_at + playbackDuration(ticks) + 3000ms`(절대 시각, 섹션 11 위험 5의 함수). 첫 진입·새로고침·PC 교체·진행권 이전·`재생 건너뛰기`가 전부 이 함수를 다시 탄다.
- **[결정]** `sealed` 진입 시 `timer_ends_at = 봉인 시각`, `timer_remaining = null`로 덮는다. 이후 `submitted_at ≥ timer_ends_at`인 행이 자동 제출분이다(섹션 06 팀 표의 "자동 제출" 표시와 §9.7 되돌리기가 쓴다).
- **[결정]** 실행 격리: `runRound.ts`는 `validate`·`run`·`score`를 Web Worker(`lib/host/run.worker.ts`)에서 부르고 3000ms 워치독을 건다. 엔진 순회(`walk`)는 0틱 블록에 상한이 없어 빈 `반복 9`를 12겹 쌓으면 9¹²번 돌며 탭이 멈춘다. 엔진은 고칠 수 없으므로(브리프 §0-1) 진행자 쪽에서 막는다.

### 9.2 팀 편집기(폰)

| 상황 | 감지 | 시스템 동작 | 진행자 행동 |
|---|---|---|---|
| 네트워크 끊김 중 편집 | `useGameChannel` status ≠ `live`, `offline` 이벤트 | `OfflineBanner` "연결이 끊겼어요 · 다시 연결 중…", 제출 비활성. 편집은 화면에만 남고 저장하지 않는다. 복귀하면 스냅샷으로 **무조건 덮고**, 버린 편집이 있었으면 "연결이 끊긴 동안의 편집은 취소됐어요"(섹션 03 §3.5). **[결정]** 섹션 05 §5.13의 flush는 끊기기 전에 예약된 저장 1건에만 적용한다 | 60초 넘게 끊긴 팀에 도우미를 보내 셀룰러 전환 안내 |
| 새로고침·브라우저 종료 후 복귀 | `/play` 마운트 | `owl.session` → `members` 확인 → 3초 안에 복귀, 커서는 스택 끝. **[결정]** `visibilitychange→hidden`·`pagehide`에서 대기 중인 저장을 즉시 보낸다(잃는 것은 최대 150ms분) | 없음 |
| 다른 브라우저·시크릿 창·인앱 브라우저로 재접속 | 자기 역할이 "이미 선택됨"이고 그 좌석은 오프라인 | localStorage가 없어 복귀하지 못한다. **[결정]** 참가 화면은 UA에 `KAKAOTALK`·`Instagram`이 있으면 상단에 "외부 브라우저로 열어 주세요" 한 줄을 띄운다 | `제거`로 유령 좌석을 비우고 다시 참가시킨다 |
| 두 명이 같은 블록 동시 수정 | 저장 UPDATE 0행 또는 `P0001` | 서버 행으로 교체 + `ConflictToast` "다른 팀원이 먼저 저장했어요". **[결정]** 내가 마지막에 넣은 블록(uid)이 서버본에 없으면 토스트에 3초간 [다시 넣기](같은 경로에 새 uid). 교체된 행이 봉인 상태면 문구를 "봉인되어 마지막 편집은 반영되지 않았어요"로 바꾼다. 150ms 안 연속 편집끼리 겹치면 토스트 없이 한쪽이 사라질 수 있다(`version < :v` 규칙, DECISIONS §D의 알려진 한계) | "한 명이 조립하고 셋은 말로"(섹션 08 FAQ) |
| 남의 블록 삭제 | 감지하지 않는다(누가 놓았는지 기록 없음) | 허용한다(브리프 §2). 지운 사람 폰에만 3초 되돌리기가 뜨고 나머지 폰에서는 블록이 사라진다 | "남의 블록도 옮기고 지울 수 있다. 팀 안의 충돌도 게임의 일부다"라고 안내한다. 반복되는 방해에만 `제거` |
| 화면 잠금·백그라운드 | `last_seen` 25초 초과 → 회색 점 | 돌아오면 즉시 하트비트, 30초 이상 공백이면 재구독과 스냅샷(섹션 03). **[결정]** `editing`·`patching` 모드에서 `navigator.wakeLock.request('screen')`, 미지원이면 무시 | 60초 미만 오프라인은 무시 |
| Architect 폰 고장 | 팀 신고, Architect 좌석 오프라인 | 문서는 서버에 있어 잃는 것이 없다 | ① 예비 폰으로 교체: `제거` → 새 폰이 Architect로 재참가(DECISIONS §I). ② 마감 직전이면 `대리 제출` **[결정]**(§9.7). 두 경우 모두 팀원 2명 이상에게 구두로 확인한다 |
| 상한 초과 상태로 타이머 만료 | 진행자 화면이 남은 시간 ≤ 0을 감지 | 폰은 0:00에서 "시간 종료 · 봉인 대기"(읽기 전용). 진행자가 `sealed`로 전이하고 `submit_program(team, round, null)`로 자동 제출 → 실행 때 `validate`가 실패해 컴파일 에러 결과(§9.4) | `전체 실행` 확인창에 그 팀이 뜬다(섹션 06 §6.7). 패치로 블록 1개를 빼면 살릴 수 있다고 알린다 |

### 9.4 실행과 재생

| 상황 | 감지 | 시스템 동작 | 진행자 행동 |
|---|---|---|---|
| 빈 프로그램·상한 초과·함수 오류 제출 | `validate` 실패(`E_EMPTY`·`E_CAP` 등) | DECISIONS §F의 컴파일 에러 결과. **[결정]** 초기 프레임과 출발 거리는 `run(map, [])`(0틱 stuck)에서 얻고, `outcome:'error'`와 `message:'컴파일 에러: ' + errors[0]`로 바꿔 `score()`에 넣는다 → 미도착 점수 `40 − 5d`. 보드는 초기 프레임 위에 곧바로 오버레이한다 | 패치권 대상(outcome error) |
| 틱이 도는 무한 루프 | 엔진 `maxTicks` 300 | `error`, "시간 초과 (300틱)". 재생은 121틱부터 4배속으로 최장 101초(섹션 11 위험 5) | `재생 건너뛰기` 또는 `다음 팀` |
| 0틱 무한 루프(빈 입의 반복 중첩) | 워치독 3000ms | 워커를 `terminate()`하고 `error`, "시간 초과 (계산이 끝나지 않음)", 0틱으로 기록한다. 점수는 컴파일 에러와 같은 방식 | 알림 배너를 확인하고 계속한다 |
| 엔진 예외 | 워커 `error` 메시지 | **[결정]** `outcome:'error'`, `message:'실행 오류: ' + e.message`(60자), 0틱, `trace = run(map, []).trace`(이것도 실패하면 `[]`), `score 0`, `score_lines [{label:'실행 오류 — 진행자 판정', points:0}]`. 진행자 화면에 빨간 배너 "{팀} 실행 오류 [재실행] [다음 팀]"과 `console.error(doc)`. autoplay는 멈추지 않는다 | `TeamDetail`에서 코드를 보고 `재실행`하거나 수동 점수 `직접 입력`(섹션 06 §6.6) |
| 손상된 doc(콘솔 조작·편집기 버그) | 폰의 `countBlocks`가 throw | **[결정]** 폰은 그 원격 doc을 받지 않고 직전 정상 로컬 doc을 `version = 원격 + 1`로 다시 저장한다(자가 치유). 토스트 "손상된 편집을 되돌렸어요". 진행자 쪽은 위의 엔진 예외 경로 | — |
| 패치 허용 후 재제출 없이 `점수판 열기` | `submitted_at is null ∧ patch_left = 0` | **[결정]** 확인창 "패치 미완료 n팀 — 기존 결과로 확정, 패치권 반환" → `submit_program(team, round, null)`로 재봉인하고 `patch_left = 1` | 해당 팀에 알린다 |

```mermaid
  B2 -->|진행자 PC 불가 또는 정전| B3[B3 실물 카드 수동 실행]
```

| 단계 | 조치 | 점수 |
|---|---|---|
| B0 | 끊긴 폰만 와이파이를 끄고 셀룰러로 접속한다. 안 되면 예비 폰으로 바꾸고 `제거` 후 재참가 | 정상 |
| B1 | 진행자 노트북은 진행자 폰 핫스팟, 참가자는 셀룰러(섹션 11 미결 7). 앱은 재연결만 하면 된다 | 정상 |
| B2 | 진행자 PC만 온라인. 팀은 규칙 카드 뒷면에 `toText` 형식(들여쓰기 2칸)으로 적거나 실물 카드로 조립 → 시간이 끝나면 Architect가 진행자에게 제출 → 진행자가 `대리 편집`으로 입력(팀당 약 40초) → 도착 순서대로 `대리 제출` → 평소처럼 `전체 실행`·보드 재생 | 엔진 그대로 |
| B3 | 전자 장비를 쓸 수 없다. 인쇄한 맵 위에서 진행자가 블록을 소리 내 읽고 도우미가 부엉이 말을 한 틱씩 옮긴다. R5 고양이는 두 번째 도우미가 경로표대로 옮긴다. 점수는 타임키퍼가 브리프 §2 표로 계산한다 | 종이 장부 |

- **[결정]** B3 준비물(D-1): 라운드별 맵 A3 5장(보드 `coding` 화면 캡처 출력), 말 2개, R5 고양이의 틱별 칸 표(`MAPS[5].cat.path`), 점수 계산표. 누적 점수는 마지막 `R{n}-scored.png`(섹션 08 §8.8)에서 이어 적는다.
- **[결정]** B3로 넘어간 게임은 복구돼도 종이로 끝낸다. DB 점수와 종이 점수를 합치지 않는다.
- **[미결]** B3에서 치를 남은 라운드 수. 수동 실행은 틱당 약 2초라 R5 한 팀에 1분이 넘게 걸린다. 권고는 현재 라운드와 1개 더.
- **[미결]** 실물 카드 인쇄 여부(섹션 11 미결 8). 인쇄하지 않으면 B2·B3는 종이 코딩으로 한다.

### 9.7 진행자 비상 버튼

전부 `RoundPanel`·`TeamDetail`에 있고 §9.1의 CAS·진행권 조건을 따른다. 새 버튼 중 확인창(섹션 06 §6.7 형식)은 `대리 제출`만 둔다: "{팀} 현재 코드 n/cap블록을 봉인한다. 검증에 실패하면 컴파일 에러로 기록된다".

| 버튼 | 활성 | DB 효과 | 화면 반응 |
|---|---|---|---|
| `이전 페이즈로` | `lobby` 외 전부 | 아래 표 | 폰·보드가 해당 페이즈 화면으로 바뀐다 |
| `제거`(팀원 내보내기) | 항상 | `delete from members where id` | 그 폰은 `/`로, 역할은 빈자리가 된다. 문서는 그대로 |
| `재실행` | `running`, 선택 팀 `results` 있음, 재생 중인 팀 없음. **[결정]** 섹션 06의 패치 조건을 넓힌 것이다 | 워커로 다시 실행 → `results` upsert(`used_patch`는 유지하되 패치 재제출 뒤면 true, `이벤트:` 줄 재부착) → `running_team_id = 팀`, `running_started_at = 서버 now` | 보드가 그 팀을 처음부터 재생한다 |
| `재생 건너뛰기` **[결정]** | `running`, 현재 팀 재생 중 | `running_started_at = 서버 now − (playbackDuration(ticks) − 2600ms)` | 보드가 끝나기 0.6초 전으로 점프하고(2틱 이상 차이는 전환 0ms), 결말 연출 뒤 autoplay 대기 |
| `+30초` | `coding` | 진행 중이면 `timer_ends_at += 30초`, 일시정지 중이면 `timer_remaining += 30`. 기존 값을 조건으로 걸어 연타해도 1회 | 폰·보드 타이머에 즉시 반영 |
| `대리 제출` **[결정]** | `coding`의 미봉인 팀, `running`의 패치 중 팀 | `rpc submit_program(team, round, null)`: 서버의 현재 doc을 봉인하고 `submit_order`를 이때 매긴다(패치면 유지) | 팀 폰에 "봉인됨" |
| `대리 편집` **[결정]** | 위와 같음 | `TeamDetail`에 `ProgramStack`과 10종 팔레트(`BLOCK_ORDER`)를 연다. 저장은 폰과 같은 `programs` 경로(버전 가드) | 팀 폰에 1초 안에 반영 |
| `여기서 진행` **[결정]** | 진행권 없는 탭 | `games.host_tab = 내 id` | 다른 진행자 탭이 오버레이로 바뀐다 |

`이전 페이즈로`의 DB 효과. `games`는 CAS로 먼저 바꾸고, 뒷정리는 멱등이라 실패하면 다시 시도한다.

| 전이 | DB 효과 |
|---|---|
| `coding → lobby`(R1) / `coding → scored`(R2~5, `round − 1`) | `timer_ends_at`·`timer_remaining = null`. **[결정]** 그 라운드 `programs` 행을 삭제한다. 다시 `coding`에 들어가면 DECISIONS §F의 upsert가 새로 만든다(되돌린 코딩은 처음부터 다시 한다) |
| `sealed → coding` | 자동 제출분(`submitted_at ≥ timer_ends_at`)만 `submitted_at = null`로 풀고, 수동 제출 팀은 봉인을 유지한다. **[결정]** `timer_ends_at = null`, `timer_remaining = 60`(일시정지, 진행자가 `재개`). `coding` 진입 함수는 부르지 않는다 |
| `running → sealed` | 그 라운드 `results` 삭제(DECISIONS §F), `running_team_id`·`running_started_at = null`. **[결정]** 이 라운드에 패치 중이거나 패치를 쓴 팀은 `submit_program(team, round, null)`로 재봉인하고 `patch_left = 1` |
| `scored → running` | 페이즈만 바꾼다. `results`와 이벤트 점수는 유지, 보드는 마지막 팀의 마지막 프레임 |
| `finished → scored` | 페이즈만 바꾼다 |
